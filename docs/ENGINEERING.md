## What this repository is

A **polyrepo living in one repository**. Each top-level directory is an
independent application with its own toolchain, dependency graph, and lifecycle.
There is no workspace file, no shared `node_modules`, no root `package.json`, and
that is deliberate: the point is to compare how the *same* architectural ideas —
SOLID, Clean Architecture, dependency inversion — land in seventeen different
runtimes and framework cultures.

What that buys us:

- A project can adopt Bun, or Poetry, or Maven, without negotiating with sixteen others.
- Each project is a self-contained reference you can copy out and run.
- Framework comparison is direct: `vue3-clean-architecture` and
  `nuxt-clean-architecture` model the same domain two ways, on purpose.

What it costs us, and what this document exists to manage:

- Nothing enforces consistency automatically. Sixteen independent toolchains drift
  in sixteen independent directions.
- A dependency bump has no blast radius beyond its project — which sounds good
  until you realise nobody notices when one project stops compiling.

That second cost is exactly what went wrong. See the [postmortem](#postmortem-how-the-repository-went-red).

## The project contract

Every top-level project directory must satisfy all of the following. CI enforces
items 1–3 mechanically; the rest are review gates.

1. **A recognised manifest at its root** — `package.json`, `pyproject.toml`,
   `pom.xml`, or `Cargo.toml`.
2. **An entry in [`.github/projects.json`](../.github/projects.json)** declaring its
   package manager, Node/Python/Java version, and which checks are enabled.
3. **An entry in the [Atlas](../learning-doc/content/atlas/)** and a row in the
   root [`README.md`](../README.md) index. All three lists must agree.
4. **A `README.md`** stating what it demonstrates, how to run it, and what it
   deliberately leaves out.
5. **Runnable from a clean clone** with the commands its README states — no
   undocumented prerequisites. If the build needs `prisma generate`, that belongs
   in a `prebuild` script, not in a reader's head.
6. **Layer discipline appropriate to its claim.** A project that says "Clean
   Architecture" has a domain layer that imports no framework. See
   [`ARCHITECTURE.md`](../ARCHITECTURE.md).
7. **UI surfaces follow [`DESIGN.md`](../DESIGN.md)** — tokens, not literals.

A directory that cannot meet 1–3 does not belong at the top level. Archive it or
finish it.

## The manifest is the source of truth

[`.github/projects.json`](../.github/projects.json) is the one file that knows what
exists and what can be checked. CI reads it, the hygiene job validates it, and the
Atlas is checked against it.

```jsonc
{
  "path": "nestjs-s.o.l.i.d",     // directory, relative to the repo root
  "name": "nestjs-s.o.l.i.d",     // display name used in CI job titles
  "ecosystem": "node",
  "packageManager": "npm",
  "node": "22",                    // toolchain floor for this project
  "checks": {
    "install": true,
    "build": true,                 // only true when it has actually been verified
    "lint": false,
    "test": false
  },
  "notes": "Prisma client is generated by the prebuild script."
}
```

**The rule that keeps CI honest: a check is only ever set to `true` once it has
been observed passing.** Flipping a flag optimistically is how a repository ends
up with red badges nobody reads. When you fix a project, run its check, then flip
the flag in the same commit.

Every disabled check carries a `notes` string explaining the blocker. A `false`
with no reason is a bug in the manifest.

## How CI works

Three workflows, each with one job to do.

### `hygiene.yml` — structural truth

Runs on every push and pull request. Fast, no installs. It fails if:

- a manifest entry points at a directory that does not exist;
- a project directory exists but is missing from the manifest;
- `dependabot.yml` targets a directory with no manifest for its ecosystem;
- the README index, the manifest, and the Atlas disagree on the project list;
- a workflow file is not valid YAML, or defines no `on:` triggers.

That last check exists because it is precisely the failure this repository shipped
for months. See the [postmortem](#postmortem-how-the-repository-went-red).

### `ci.yml` — per-project verification

1. A `changes` job diffs the pull request and emits the list of projects whose
   files were touched.
2. A matrix job runs only for those projects, with `fail-fast: false`, using the
   toolchain and checks declared in the manifest.

Touch nothing but docs and no project job runs. Touch one project and one job
runs. This is what makes per-project CI affordable across seventeen toolchains.

### `dependabot` — grouped, never auto-merged

Configuration lives in [`.github/dependabot.yml`](../.github/dependabot.yml).

## Working on a change

```bash
# 1. Branch from main.
git switch -c <type>/<short-description>

# 2. Work inside exactly one project directory where possible.
cd <project> && npm install && npm run build

# 3. Run the same checks CI will run for that project.
node .github/scripts/check-manifest.mjs      # structural checks, no install needed

# 4. Commit with a scope that names the project.
git commit -m "fix(nestjs-solid): generate prisma client before build"
```

### Commit convention

`<type>(<scope>): <imperative summary>`

`type` ∈ `feat` · `fix` · `docs` · `refactor` · `test` · `chore` · `ci` · `deps`
`scope` is the project directory, or `repo` for cross-cutting changes.

### Pull request expectations

- One project per pull request wherever possible.
- The description states which checks you ran and what they printed.
- If you flipped a manifest flag from `false` to `true`, say what you fixed.
- Green CI is necessary, not sufficient — see the [review gates](#the-project-contract).

### Architecture decisions

Anything that changes a layering rule, adds a project, removes a project, or
diverges from a convention another project already follows gets an ADR in
[`docs/decisions/`](decisions/). Copy [`0000-template.md`](decisions/0000-template.md).
An ADR is short. If it takes more than a page you are describing an
implementation, not a decision.

## Dependency policy

1. **Minor and patch updates are grouped per project** into a single weekly pull
   request. Before grouping, this repository generated one pull request per
   dependency per project per week; the backlog reached roughly 1,200.
2. **Major updates arrive alone.** Framework packages — `next`, `@angular/*`,
   `@nestjs/*`, `react-native`, `nuxt` — are deliberately excluded from the
   minor/patch groups so a major bump is always reviewable in isolation.
3. **Nothing merges without a green run for the touched project.** "No checks
   ran" is a blocker, not a pass.
4. **Toolchain floors are pinned in the manifest**, not discovered in CI logs.
5. **A held dependency needs a written reason and a clearing condition.** Two are
   currently held; both are recorded in [known open work](#known-open-work).

The [`dependency-steward`](../.claude/agents/dependency-steward.md) agent carries a
table of every breakage this repository has actually hit. Read it before
diagnosing a dependency failure — the answer is usually already there.

## Agent-assisted development

Repository-scoped subagents live in [`.claude/agents/`](../.claude/agents/), modelled
on the division structure of
[msitarzewski/agency-agents](https://github.com/msitarzewski/agency-agents) and
specialised for this codebase rather than copied wholesale.

| Agent | Use it when |
|:---|:---|
| [`architecture-reviewer`](../.claude/agents/architecture-reviewer.md) | A diff moves code across layers or adds a dependency to an inner layer |
| [`ui-finish-gate`](../.claude/agents/ui-finish-gate.md) | Any component, page, or stylesheet changed |
| [`dependency-steward`](../.claude/agents/dependency-steward.md) | A dependency PR needs a decision, or a package stops resolving |
| [`atlas-curator`](../.claude/agents/atlas-curator.md) | A project is added, removed, restructured, or its docs have drifted |

The design contract these agents enforce for UI work is [`DESIGN.md`](../DESIGN.md),
written in the [awesome-design-md](https://github.com/VoltAgent/awesome-design-md)
format so any coding agent can consume it directly.

To install the upstream agency-agents catalogue alongside these:

```bash
git clone https://github.com/msitarzewski/agency-agents /tmp/agency-agents
cp /tmp/agency-agents/engineering/*.md ~/.claude/agents/
```

Repository agents in `.claude/agents/` take precedence for work inside this repo.

## Postmortem: how the repository went red

Worth writing down, because every rule above is a direct consequence.

**Symptom.** Every push to `main` produced a failed Actions run. The owner had
already removed the deploy pipeline, so the failures looked inexplicable.

**Cause.** `.github/workflows/deploy.yml` had been *commented out* rather than
deleted. A workflow file whose `on:` block is commented out is not an inert file —
it is an **invalid** workflow. GitHub parses it, finds no event triggers, and fails
the run instantly. Every one of those runs finished in zero seconds with no jobs,
which is the signature of a parse failure rather than a build failure.

For extra measure, had it ever been uncommented it would still have failed: it
built a directory called `learning-platform/`, which had since been renamed to
`learning-doc/`.

**The second-order damage.** Because the only workflow was permanently red, red
stopped meaning anything. Dependabot kept merging — including majors: TypeScript 7,
Vite 8, Astro 7, Next 16, ESLint 10, Angular 22. Nothing verified any of it. By the
time it was investigated:

- **4 of 16** JavaScript projects could not `install`
- **6 of 16** could not `build`

Not one of those breakages was caused by a code change. Every one came from an
unverified dependency bump.

**Lessons, now encoded:**

| Lesson | Where it lives now |
|:---|:---|
| Delete workflows, never comment them out | `hygiene.yml` fails on a workflow with no `on:` triggers |
| A permanently-red check is worse than no check | CI is manifest-driven so it is green from day one |
| Automation without verification is a liability | Grouped Dependabot, majors isolated, nothing auto-merged |
| Docs that name deleted directories are misinformation | `check-manifest.mjs` cross-validates README ↔ manifest ↔ Atlas |
| Broken states must be visible, not silent | Every disabled check carries a `notes` reason |

## Known open work

Tracked here rather than hidden behind a disabled flag.

| Project | Issue | Status |
|:---|:---|:---|
| `sveltekit` | `arctic@3` no longer exports `Google` from the package root; `src/lib/server/oauth.ts` needs migrating to the current provider API. | `build: false`. Install and lint are green. |
| `angular-s.o.l.i.d-advanced` | Angular CLI 22 requires Node ≥22.22.3. CI pins Node 24 for this project; it could not be verified on the 22.22.2 sandbox used to repair the repo. | `build: true`, unverified locally — first CI run confirms or refutes. |
| `hospital-management` | `billing-service`, `clinical-service`, and `scheduling-service` contain sources but no `pom.xml`, so they cannot build or be tracked by Dependabot. | Excluded from the manifest until their POMs land. |
| All Node projects | No lockfiles are committed, so installs are not reproducible and CI cannot use `npm ci`. | Deliberate for now; committing them is a per-project decision worth an ADR. |
| `typescript` | Held at `^6` in `nestjs-s.o.l.i.d` and `vue3-clean-architecture`. Nest CLI and `vue-tsc` both need the programmatic compiler API that TS 7.0 removed. | Clears when TS 7.1 restores the API. |
| `prisma` | Held at `^6` in `nestjs-s.o.l.i.d` and `next-prisma-starter`. Prisma 7 removed the datasource `url` from `schema.prisma`; the connection string moves to `prisma.config.ts` and the client needs a driver adapter. That is a runtime migration, not a version bump. | Clears when the adapter migration is done deliberately, with an ADR. |
